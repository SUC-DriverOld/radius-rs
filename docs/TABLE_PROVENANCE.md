# Constant table provenance

`src/vocoder/crossover_tables.rs` compiles in six constant tables. They are the only
engine data that is not computed from a formula, and this file records where every
number came from.

The tables live as Rust source in `src/vocoder/table_data/`, generated by
`tools/gen_table_source.py`. **Nothing is read from disk at build or run time**:
there is no build script and no asset directory, so `radius.exe` and `radius_rs.dll`
work when copied anywhere on their own.

| table | source symbol (reference engine) | layout | elements | bytes in the binary |
|---|---|---|---|---|
| `XOVER_FIR_48K` | `rx_xover_fir_taps` | `[4][2048]` `f32` row-major | 8192 | 32768 |
| `XOVER_FIR_44K` | `rx_xover_fir_taps_44k` | `[4][2048]` `f32` row-major | 8192 | 32768 |
| `VC_WIN_48K` | `rx_vc_default_win_table` | `f32`, 4 bands × 7184 | 28736 | 114944 |
| `VC_WIN_44K` | `rx_vc_default_win_table_44k` | `f32`, 4 bands × 6599 | 26396 | 105584 |
| `VC_SYNTH_WIN_A_44K` | `rx_vc_synth_win_a_44k` | `f32` | 6599 | 26396 |
| `VC_SYNTH_WIN_B_44K` | `rx_vc_synth_win_b_44k` | `f32` | 6599 | 26396 |

Every one of these is read by the engine:

| table | read by |
|---|---|
| `XOVER_FIR_*` | `fir()` → `Crossover` |
| `VC_WIN_*` | `win()` → `VocoderState::new` |
| `VC_SYNTH_WIN_*_44K` | `synth_44k()` → `VocoderState::new` at 44.1 kHz |

## What they are

* **Crossover FIR banks** — the four band-splitting filters the vocoder feeds its band
  rings with, selected by sample rate. `Crossover::new` reverses each band, as the C
  does in `rx_crossover_create`; the tables hold the header's original (unreversed)
  order.
* **Vocoder window table** — the analysis/synthesis window bank for the four bands,
  `n_write` samples per band (7184 at 48 kHz, 6599 at 44.1 kHz).
* **44.1 kHz synthesis windows** — the `a`/`b` pair. At 48 kHz the equivalent pair is
  generated by formula in `VocoderState::build_synth_windows`, but the 44.1 kHz pair
  is table data.

Every table is also *derivable* rather than arbitrary: `src/tables.rs` computes the
TD envelope spans, the Hann records, the pitch windows and the transients-info Kaiser
windows at run time, so only genuinely tabulated data lives here.

## What is deliberately not here

The reference engine has two more numeric tables, and neither is in this crate
because neither is read by any code path:

* **`rx_vc_sched[]`** (`vc_schedule.h`) — the research corpus' per-granule schedule,
  28993 rows × 4 `i32`. The engine computes its schedule with `rx_vc_calc_sched`
  (ported as `radius_rs::vocoder::vc_calc_sched`) and `vocoder_core.c` states that it
  does not reference the header's table. It is archived in
  [`reference/vc_schedule.bin`](reference/README.md) instead.
* **`rx_vc_sched_m3` / `rx_vc_sched_m6`** (`vc_sched_neg.h`) — the negative-semitone
  variants (−3 and −6 semitones), likewise not referenced by the engine. The closed
  form already covers `ratio < 1`, so these are not needed either.

Both were research artifacts used to *derive* the scheduler; the derived
implementation is what the crate ships. The archives keep the record without
shipping the payload.

A note on cost, because it is easy to assume the wrong thing: keeping these in `src/`
as `const` arrays did **not** make the binaries bigger. `radius.exe` and
`radius_rs.dll` were byte-for-byte the same size before and after their removal
(2 868 736 / 749 056 bytes in the default build), because an unreferenced `const`
that nothing calls is dead code and the linker drops it. A search for the schedule
bytes inside both artifacts finds nothing, while the live FIR taps are present. So
this was a **code hygiene** change — no dead weight in `src/`, no misleading
"reference data" in a shipping module — not a size optimization.

## How the numbers were obtained

The values were parsed out of the reference engine's C headers by the strictest
available path: the decimal literal is read as `f64` and rounded once to `f32` (which
is what `numpy.float32(...)` does, and was verified to agree with a direct `f32` parse
of every literal in all six headers). The parse was checked three ways — against the
C headers, against the `pyradius` cache (`pyradius/src/pyradius/_tables/*.npz`) and
against the running engine's output — with zero mismatches.

The headers, recorded for provenance only:

    libradius/src/ops/crossover_fir_table.h
    libradius/src/ops/crossover_fir_table_44k.h
    libradius/src/engine/vc_win_table.h
    libradius/src/engine/vc_win_table_44k.h
    libradius/src/engine/vc_synth_win_44k.h

This crate does not read them, and the `libradius`/`pyradius` projects they come from are not part of it: they can be absent without affecting the build or the tests.

The parse produced packed little-endian binaries, which `tools/gen_table_source.py`
converted once into the committed `.rs` files. Those `.bin` files are **not part of
the crate** — they were the one-off parse artifact. If you ever need to re-run the
conversion, regenerate them from the headers the same way and pass `--bin-dir`; the
committed `.rs` files are the source of record, and Rust no longer depends on the
binaries existing.

## Regenerating and verifying

The values are written as exact bit patterns, so a regeneration is either
byte-identical or visibly wrong:

* `f32` tables become `f32::from_bits(0x…)` — no decimal formatting step exists that
  could round a value a second time;
* `i32` tables become plain integers.

```bash
# with the packed binaries available (--bin-dir, default ./data):
python tools/gen_table_source.py                 # rewrite src/vocoder/table_data/*.rs
python tools/gen_table_source.py --check         # byte-for-byte compare, no writes
```

`--check` is what makes the conversion auditable: it regenerates the expected text in
memory and compares it with what is on disk, so a hand edit or a bad regeneration is
caught rather than trusted.

The Rust side does not rely on that tool alone. `crossover_tables.rs` asserts every
array length in a `const` block (a wrong or truncated table is a **compile error**),
and the tests check the element counts, the per-rate distinctness and spot values read
straight from the headers.
